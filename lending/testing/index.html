Testing and launch

Integration testing is required before sending customer applications. Use an environment and test data explicitly approved by AC and the downstream platform.

Minimum acceptance checklist

  • The AC client ID and API key are stored only on the backend.
  • Missing and incorrect API credentials are rejected.
  • Valid credentials associated with another client ID are rejected.
  • An unauthorised or disabled client cannot submit an application.
  • Malformed XML, duplicate fields and reserved campaign_code/mode fields fail safely.
  • POST /post handles approved application data and returns XML.
  • Initial XML result=10 yields an AC results_url; polling with the original client succeeds.
  • Results tokens cannot be used by a different client.
  • Immediate final offers and final no-offer responses both render correctly.
  • Alternative offers without normal loan repayment figures do not appear with misleading numbers.
  • HTTP timeouts or ambiguous submission outcomes never trigger automatic duplicate submissions.
  • Client systems handle expired results tokens and 429 throttling safely.

Postman request setup

Setting Value
Method POST
URL https://api.authorisedcompliance.com/post
Headers X-AC-Client-ID, x-api-key, Content-Type: application/xml
Body Raw XML application with approved test data

Do not test using real consumer data unless AC has explicitly approved the environment, customer consents and test conditions.

Before launch

Confirm the client-specific permitted route, production credentials, source-IP restrictions (if any), rate limits, polling interval, results-token lifetime, and the handling of alternative lender products. AC should also confirm that the relevant client activity is approved under the applicable downstream commercial arrangements.
